# i18n Design: localizing plugin UI strings

Status: spike output from [plan 014](../plans/014-i18n-design-spike.md). Follow-up implementation plans should cite this document as their source.

## Problem

The repo ships trilingual READMEs (`README.md`, `README.ja.md`, `README.ko.md`) but the plugin UI is English-only: command names, modal buttons, settings labels, and notices. Japanese/Korean users arriving through the localized READMEs get an English-only tool. Obsidian has no official i18n string API, so a local locale→string map is the standard approach.

## 2. Mechanism comparison

### Option A: local string map + locale detection

`src/utils/i18n.ts` exporting `t(key, locale?)`, typed `as const` en map, en fallback, ja/ko maps added later. Locale detection reuses the `getCurrentLocale` approach already in `src/utils/deepl_languages.ts` (moment locale → `navigator.language` → `''`).

- Pros: zero dependencies; matches Obsidian ecosystem norms; detection infrastructure already proven in this repo (DeepL auto-language).
- Cons: strings compiled into the bundle (fine for a small plugin); contributors must keep maps in sync (mitigated by `as const` typing + a fallback unit test).

### Option B: community-plugin conventions (web check, 2026-08)

Checked the Obsidian plugin ecosystem's i18n practice. Findings:

- The official `obsidian` module exports `getLanguage()` (obsidian.d.ts:3365), and the official eslint plugin prefers it over reading localStorage or a browser-language detector.
- Community best practice: ship localization inside the plugin source (typed locale modules bundled with `main.js`), keep English as the canonical complete locale, every other locale has the same key set and falls back to English (mirrors Obsidian's own translation workflow: "untranslated English is preferable to broken content").
- Real plugins (e.g. phibr0/obsidian-dictionary) localize via the app's internal language with locale files in-repo. No i18n dependency is recommended for the scale of a small plugin.

Conclusion: Option B endorses Option A's shape (in-repo typed locale maps + English fallback), with one refinement — prefer `getLanguage()` over `navigator.language` when Obsidian's API is available (this repo's `getCurrentLocale` uses the moment/navigator fallback chain because `getLanguage` was not part of the existing precedent; the follow-up can switch the detector to `getLanguage()` without changing the map format).

### Option C: English-only + manual override

Keep all strings English; add a "UI language" setting users set by hand. No auto-detection.

- Pros: simplest possible; zero risk of a wrong auto-detected language; users who want ja/ko pick it explicitly.
- Cons: an English-first user arriving from `README.ja.md` sees no difference until they find the setting; contradicts the repo's trilingual-README posture; still needs the same map + `t()` machinery, just with a manual switch instead of detection.

### Recommendation

**Option A (local string map + locale detection)**, implemented in the shape Option B validates: `src/utils/i18n.ts` with a typed en map, `t(key, locale?)`, en fallback, ja/ko added later.

- A over B-as-a-distinct-choice: B is not a separate mechanism, it *is* A — the community's answer is in-repo typed locale maps, so there is no second mechanism to pick.
- A over C: the repo already ships ja/ko READMEs and already auto-detects the UI locale for DeepL (users trust auto-detection for their translation target today); a manual-only override would hide localization behind a settings hunt. C's "manual override" half is still worth noting: the follow-up plan should add a `uiLanguage` setting (`auto` default) so users can force a language when detection is wrong.

## 3. First slice scope

Migration order (highest user visibility first):

1. **Commands + search modal** (8 strings, 2 files) — the surfaces every user touches; the smallest coherent slice, and the PoC already wires the modal.
2. **Settings tab** (~43 strings, 1 file) — biggest chunk; a full-file pass keeps the diff mechanical.
3. **Notices/errors** (5 strings, 3 files + `main.ts` fallback dedupe) — last, because `ConfigurationError` messages surface through `showNotice` and there is a decision to make: **keep `ConfigurationError` messages in English** (they tell the user to fix plugin settings, where the settings tab itself will be localized by then; error strings also appear in `console.error` output) — but localize the generic user-facing fallbacks (`An unexpected error occurred.`, `Failed to read the template file`, modal notices) since those are pure UI chrome. The follow-up plan should keep this split explicit.

### Follow-up implementation plan must include

- **File layout**: `src/utils/i18n.ts` (map + `t`), `src/locales/en.ts`, later `src/locales/ja.ts`, `src/locales/ko.ts`; one `locales/<lang>.ts` file per language, `as const`, flat dotted keys (`'command.createGameNote'`, `'settings.folder.name'`).
- **`t()` contract**: `t(key, locale?)` with locale normalization identical to `mapLocaleToDeepLTargetLanguage` (trim, lowercase, split on `-`), en fallback, missing-key → en string; never throw.
- **Test expectations**: a `t()` unit test asserting (a) en locale returns the en string, (b) a ja locale with no ja map falls back to en, (c) an unknown key returns the key itself or the en fallback — pick one and assert it. The jsdom test environment cannot be trusted for locale detection (no real moment locale; `navigator.language` is `en-US`), so tests pass `locale` explicitly; detection itself gets one smoke test at most.
- **README note for contributors**: a "Translations" section in `CONTRIBUTING.md`-style docs (or the README) stating that new UI strings must add a key to `locales/en.ts` and every other locale file, mirroring the existing trilingual README sync rule.
- **Detection upgrade**: switch the detector to Obsidian's `getLanguage()` when available, falling back to the moment/navigator chain — a follow-up change to `i18n.ts` only, not to `getCurrentLocale` (that one stays as the DeepL precedent).
- **Scope guard**: settings enum values (`Snake Case`/`Camel Case`) stay English as stored data; only add display mapping if users ask.

## 4. Coordination rule

Trilingual README sync is the repo convention: each new setting or command gets its README row planned at the same time. From now on, **every new user-facing string gets its i18n key planned in the same change** — the follow-up plan must treat "add string" and "add key + README row" as one unit of work, so the READMEs, the string maps, and the UI never drift apart.

## 5. Proof-of-concept (this spike)

Built per plan Step 4: `src/utils/i18n.ts` (en map only, `t(key, locale?)`, locale normalization copied from the DeepL precedent), wired into `src/views/game_search_modal.ts` (`SEARCH_BUTTON_TEXT`, `REQUESTING_BUTTON_TEXT`, heading), plus `src/utils/i18n.test.ts` (en lookup, ja→en fallback). No settings toggle: with an en-only map every locale resolves to the same strings, so a toggle would be dead UI until ja/ko maps exist — it moves into the follow-up as the `uiLanguage` setting. Behavior for English users is identical (verified: existing `game_search_modal.test.ts` passes unchanged).

## Honest verdict

The local-map mechanism is right, but the *timeline* should be modest: this is a solo-maintained plugin with ~50 strings and two more languages to maintain. If ja/ko contributor translations do not materialize, the map stays en-only and the `t()` indirection is still worthwhile — it pins down the string inventory and makes a later translation pass a purely additive change. If the maintainer decides translation is not worth the maintenance, English-only + manual override (Option C) is the fallback position, not a failure: the inventory in this document still applies either way.
